# 签到数据库实现与验证

验证日期：2026-10-13。范围：新增迁移 `243_checkin_rewards.sql`、PostgreSQL 签到 repository；没有连接、迁移或修改现有用户数据库。

## 持久化与资金边界

- 每日签到唯一键为 `(user_id, business_date, reward_type)`，事务中的全局活动 advisory lock 串行规则、预算、领取和周期结算，用户行锁与原有余额扣费互斥。
- 先返回当天原签到记录，再判断活动和资格。重复请求不重抽、不重复加款，活动关闭后原领取仍可重试。
- 预算在随机抽奖前按奖池最大金额检查，避免在预算不足时反复重抽。每日支出和周期预留均使用 PostgreSQL `NUMERIC(20,8)`。
- 奖励直接以 SQL 增加 `users.balance`，同时写独立奖励账本与持久缓存失效 outbox，不经过充值方法、不增加 `total_recharged`、不产生邀请返利。负余额允许部分回补。
- 原始付款资格以已实际履约的余额订单为准，要求 `completed_at`、`paid_at` 和正 `pay_amount`，排除订阅与赠款。付款新增和更新触发器在同一事务实时同步独立来源贡献表，迁移精确回填已履约历史；资格从该表求和，退款中间态立即撤销贡献。
- 同一奖励事务写入项目原有 `auth_cache_invalidation_outbox`，只存 API key 的 SHA-256 摘要，复用其两阶段持久失效 worker。签到 outbox 独立重试 billing 缓存失效，不把吞掉底层错误的同步 auth 方法当成已确认交付。

## 退款口径核验

源码 `backend/internal/service/payment_refund.go` 的退款计划区分 `RefundAmount` 与 `GatewayAmount`：前者为到账余额美元，后者按订单 `amount/pay_amount` 换算支付网关币种。落入 `payment_orders.refund_amount` 的是 `RefundAmount`，因此有效付费余额使用：

```text
max(amount - bonus_amount, 0) × max(1 - min(refund_amount / amount, 1), 0)
```

不能直接用 `refund_amount/pay_amount`，否则人民币等支付订单会错误计算资格。测试例：支付 72（支付币种）、到账 $10、其中赠款 $2、余额退款 $2.50，有效付费余额为 $6。

仅 `COMPLETED` 与 `PARTIALLY_REFUNDED` 订单可贡献资格。`REFUND_REQUESTED`、`REFUNDING`、`REFUND_PENDING`、`REFUND_FAILED` 和已全退订单贡献为零；退款失败可能包含余额扣减回滚失败，资格保守挂起，待付款状态修复。

## 请求与周期

- 用量成功插入后触发持久日桶计数。全零失败占位不计；实际费用、免费 token、缓存 token、图像 token 或 image_count 有效量均可计。相同用户和 request_id 去重，没有 request_id 时使用用量行 ID。
- 去重键和日桶与用量原表独立，因此用量清理、分区删除不抹掉活动资格。活动关闭且用户没有对应已预留周期时不写计数，避免全站无效双写。超过 35 天且没有未结束周期覆盖的日桶先标为不可变快照，独立短事务每批最多清理 5,000 个去重键；之后重放该日期不能再次计数。迁移不回填历史用量，避免把开启前行为计入新周期。
- 七日周期启动时锁规则并预留完整周期奖金。预留失败仍支付每日奖励，但周期明确显示 `capacity_exhausted`，没有周期奖金承诺。
- 闭合自然日没有签到可确定断签，释放预留。满周期签到且请求全部达标，在约定次日 01:00 后结算，并发、重复补扫不会重复奖励。
- 现有异步用量写入没有可证明全量入库的 writer drain 水位。低于请求门槛不能在 01:00 推断失败，使用 `pending_usage` 保留预留并持续补扫；迟到用量补齐后仅发一次。管理员可带原因重试核对，或者确认闭合日期请求确实不足后取消未确认资格、释放预留。操作独立落审计；不能强制虚假入账，不能取消已经达标的应付奖。取消前锁定全部日桶，避免与迟到用量并发判断。
- 为避免未确认周期被重叠新周期替代，`active` / `pending_usage` / `blocked_user` 周期未结束前不启动新周期。账户禁用或软删除时挂起预留，恢复后继续核对；断签与预算名额不足的周期可在下一次每日签到时重新入场。
- 周期扫描每次最多 100 条，按处理时间和 ID 轮转，避免永远卡在前 100 条待核对周期。去重清理使用独立短事务，不持有全局活动锁。

## 已完成验证

使用本次新建的 PostgreSQL 18 容器，绑定回环地址随机端口，入口数据库名称强制 `checkin_test`。业务测试每次创建随机 schema，并只清理本测试 schema。完整迁移链每次创建隔离的新数据库，结束后删除；专属 `checkin_test` 的 public schema 另行重建完整迁移用于主线程 HTTP 联调，容器在联调完毕后清理。

运行：`go test ./internal/repository -run '^TestCheckin' -count=1`。数据库测试需显式设置 `CHECKIN_TEST_DSN`，未设置时跳过；SQL mock 测试正常运行。最后一次全部通过，耗时 13.539 秒。

- SQL mock：关闭活动后的原记录重试、版本冲突回滚、无规则默认关闭。
- PostgreSQL：20 个并发同用户请求仅 1 次抽奖、1 次入账；余额为负时正常回补。
- 预算不足在抽奖前拒绝；独立账本/outbox 与奖励数量一致；累计充值不变。
- 七日周期完整流程、usage 清理后计数仍存、重复 request_id 去重、迟到请求延迟后补发。
- 10 个并发结算和再次重复补扫仅 1 笔周期奖励；断签释放预算；名额不足保留每日奖。
- 非美元支付金额的部分退款、全额退款、中间退款状态、退款失败、订阅与未履约订单资格。

- 历史记录游标分页；次日新规则生效、午夜边界、立即关闭、预定启用不能提前覆盖关闭状态。

- 管理员原因必填、重试审计、取消预留、重复取消拒绝；账号禁用/软删除不发奖，恢复后结算。

- 关闭活动没有待预留周期时不双写用量，35 天快照固化并清理去重键，过期请求重放不增加计数。
