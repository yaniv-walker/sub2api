# 06｜P5：生产监控、告警与容量复核

- **类型：**运维待办 + 监控设计；仅在发现仓库缺失功能时拆开发任务
- **优先级：**P5（持续工作）；可与 P0 并行梳理现状，但容量决策依赖有效基线
- **状态：**待实施

## 1. 目标

建立能发现故障、区分入口/应用/上游的监控与处置流程；以趋势证据决定扩容。先前一次只读快照显示机器/容器无明显资源饱和，不足以排除峰值、瞬时网络或长期容量问题。

## 2. 监控面板

复用项目已有监控/日志栈。先清点现有 exporter、指标端点、云监控与告警渠道，避免重复部署。

### 应用 RED
- 请求 Rate、Error、Duration（按协议、路由模板、流式标志、状态类）。
- TTFT、chunk gap、完整流时长；按有限枚举维度查看。
- 上游 attempt、502/503、retry/switch、失败原因及各阶段 latency。
- 终止原因：完成、客户取消、下游写失败、上游错误、deadline、未知。

### 主机/容器 USE
- CPU（利用率、throttle、load）、内存/工作集/OOM、磁盘容量与 I/O、文件描述符。
- 网卡吞吐、drop/error、TCP retrans/reset 等**按时间窗口增量和方向**；不可用开机累计总值直接设告警。
- 容器 restart/OOM/health、应用连接池、goroutine/线程等现有可安全观测项。
- 依赖 PostgreSQL/Redis 可用性、连接池与慢查询（按现有设施/权限治理）。

### 外部探测
- 从代表性区域和运营商做低频、低成本的 HTTPS/TLS/协议合成探测；不发真实付费大模型请求，或使用有成本上限的专用无副作用探针。
- 客户路径问题不能仅由服务器本机 loopback 或单区域探针代替。

## 3. 告警设计

- 先采集稳定基线，按错误预算/业务 SLO 与峰谷设阈值；阈值和持续窗口由服务 owner 批准，避免无证据的固定数字。
- 告警至少区分：入口可用性/建连恶化、应用错误率、上游 5xx、TTFT/长间隔长尾、资源瓶颈、依赖不可用。
- 加入最小持续时间、抑制/聚合和去重，避免单个客户取消触发值班风暴。
- 每条告警写明用户影响、诊断链接、只读首查步骤、升级 owner、止损/回滚边界。
- 监控端点不得意外暴露公网；遵循现有鉴权、网络 ACL、secret 管理。

## 4. 容量判断规则

不因单次低负载快照结论“永不需扩容”，也不因断连直接扩规格。持续观察峰值与长尾并检查：CPU 饱和/steal/throttle、内存回收/OOM、网络带宽/丢包、FD/连接池上限、数据库等待、上游等待占用并发。只有瓶颈信号与故障时间相关、且扩容可针对该瓶颈时才提出规格或水平扩展建议。

## 5. 值班运行手册

- [ ] 客户反馈慢/断连：收集时间窗、地区/运营商、SDK/协议、脱敏 request ID；不索取 API Key/正文。
- [ ] 查同一 ID 的入口、handler、upstream attempt、终态，判别先后顺序。
- [ ] 看相同时间窗区域探测、接口/运营商分组及资源趋势。
- [ ] 区分单客户/单运营商/全站/单上游事件；必要时升级对应 owner。
- [ ] 变更前记录指标和状态；执行需有明确授权、影响面、回滚步骤与观察人。
- [ ] 事件后保存脱敏时间线、根因置信度、缓解动作、遗留验证项。

## 6. 验收

- 主要 RED/USE 面板能按预设维度查询，标签基数受控；指标命名与 [01](01-observability-design.md) 一致。
- 模拟入口失败、上游 503、流式 stall、客户端取消、资源逼近阈值时，告警路由正确且不泄漏敏感数据。
- 至少完成一次桌面演练：值班人员能按 runbook 从 request ID 定位故障层并说明未知项。
- 告警阈值依据基线/业务 SLO，有责任人和复核日期；资源扩容决策有量化证据及成本比较。
- 监控组件本身有容量、保留期、权限和故障降级说明。
