# 05｜P4：403/404 客户请求错误分流与整改

- **类型：**诊断/产品配置待办；预计无需先开发，但发现代码缺陷再立项
- **优先级：**P4；与网络断连独立处理
- **状态：**待归因

## 1. 已知线索与限制

此前生产访问摘要中 `/v1/responses` 有较多快速 403，`/v1/v1/usage` 有 404。这里只作为待验证线索，不证明所有 403 都是 API Key 错误，也不证明所有 404 都源自重复 Base URL。需对具体路由、返回错误类别、分组配置与客户端配置取样，脱敏后核验。

## 2. 排查矩阵

### 403 `/v1/responses`
- [ ] 确认请求实际匹配的 handler/路由版本及 403 响应的内部错误分类（不可保存/展示 Key）。
- [ ] 检查 API Key 状态、所属组、额度/权限、模型允许列表及 Responses API 协议支持条件。
- [ ] 对比同 Key 同模型的 `/v1/chat/completions` 与 `/v1/responses` 是否存在能力差异。
- [ ] 检查上游/应用是否返回 403，并区分 gateway 自身拒绝与上游拒绝。
- [ ] 为每个拒绝原因给用户明确但不泄漏安全策略细节的错误说明。

### 404 `/v1/v1/usage`
- [ ] 查看客户端最终请求 URL 的 path（查询值脱敏）；确认客户端 base URL 是否已含 `/v1`、SDK 是否再自动追加 `/v1`。
- [ ] 对照服务端公开支持路径、代理 rewrite 和版本；不得为了掩盖错误而增加重复别名。
- [ ] 复现不同 SDK/客户端版本并给出正确 Base URL 示例。
- [ ] 如果是 API 路由缺失而非客户端拼接，确认该端点产品契约与认证要求后再单独设计实现。

## 3. 交付物

- 按错误类别、接口路径模板、客户端类型版本的脱敏汇总；不含客户 IP、Key、用户 ID、完整 URL query。
- 根因分类：用户/SDK 配置、API Key/权限、路由契约、应用 bug、上游返回、未知。
- 每类修复责任人、最小复现、文档/代码改动、回归案例。

## 4. 验收

- 403 与 404 不再被归入网络断连指标；其原因分类可通过日志或受控诊断复核。
- 对支持/不支持的 Responses API、错误 Key/组/模型和错误 Base URL 建立测试矩阵。
- 未改变现有路由语义或兼容客户端契约；若新增 endpoint/alias，须独立 API 设计、文档、鉴权与兼容性审查。
- 用户可据错误提示修正配置，且错误消息不泄漏密钥、账号池或内部地址。

## 5. 范围外

不通过放宽所有权限、绕过模型 allowlist 或将未知 404 一律重写到其他路由来“修复”。不把 403 计为连接失败，不以新增别名掩盖 SDK 基础 URL 配错。
