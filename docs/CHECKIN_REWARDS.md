# 每日签到与连续活跃奖励

## 启用

本功能默认关闭，不会自动向现有用户发奖。管理员在「签到规则设置」发布规则：最低有效充值、奖励档位与概率、当日新发放/承诺预算、生效时间，以及可选的动态加成与连续活跃奖励。

- 用户入口：`/checkin`；关闭活动仍可直接查看自己的历史。
- 管理入口：`/admin/checkin/settings`、`/admin/checkin/rewards`。
- 默认北京时间次日零点生效；首次发布可指定未来生效时间。后续开启/修改不能早于次日。关闭立即生效，保留已发奖励与周期预留。
- 动态加成和连续奖励默认关闭。三项加成分档初始为空，运营显式配置后才影响概率。
- 活动固定 `Asia/Shanghai`，日期与时间均由服务器决定。客户端的时区、时间、金额和用户 ID 不参与领取判定。

## 默认参考配置

最低有效付费额度 `$5.00`、每日预算 `$100.00`。奖池金额依次为 `0.01/0.15/0.20/0.30/0.40/1.00 USD`，整数 BPS 权重 `8500/700/400/200/150/50`，合计 10000。基础单次期望 `$0.0440`。所有金额与概率是本项目建议默认值，不声称与参考站后台一致。

连续周期默认 7 天，每日 300 次有效请求，周期奖励 `$0.50`，第七天结束后的次日 01:00 结算。实际启用需要运营确认预算与规则。转盘等分色块仅展示奖项，不代表等概率；客户端展示服务器已确认金额。

## 实现与财务边界

新增迁移 `243_checkin_rewards.sql` 由原迁移系统自动运行，**不要修改已应用的迁移**。数据通过独立 SQL repository 管理，未为这些独立奖账表生成庞大的 Ent CRUD 层；沿用现有 Go Handler → Service → Repository 和 Wire 注入。

- 同日同用户只一条 daily 记录。事务内锁定规则、预算和用户，服务端安全随机抽样，增加余额、写奖励账与缓存事件；跨实例重复领取返回原记录。
- 奖励不经过充值/兑换码方法，不增加 `total_recharged`，不触发邀请返利。允许用户负余额部分回补。金额使用整数 1e-8 单位与 PostgreSQL NUMERIC，接口使用字符串。
- 抽奖前须能覆盖奖池最高金额；预算不足直接暂停新领取，避免重试反复抽到低金额的偏差。
- 周期启动预留完整周期奖金，日预算同时限制新发奖和新承诺。结算将原预算日预留转实际支出，不再次扣款。无预留名额仍可领每日奖，但界面明确本周期无奖金承诺。
- 奖励在同一事务写入原生 auth cache 失效 outbox 和独立 billing outbox。缓存失败可重试，不能将数据库已入账提示成未到账。
- 领取后前端刷新用户余额；网络结果不明先查询 status，不能用客户端动画完成回调确认入账。

## 充值资格与历史

只认可已支付、已实际履约的余额订单对应的基础 USD 额度，排除赠送、订阅、签到、管理员赠款和无明确支付来源的兑换。支付新增/更新触发器同步来源贡献，迁移回填符合条件的历史订单。

经真实退款代码核验，`payment_orders.refund_amount` 是余额 USD，`pay_amount` 为网关支付币种。因此贡献为：

```text
max(amount - bonus_amount, 0) × max(1 - min(refund_amount / amount, 1), 0)
```

退款处理中或退款失败需要核对的状态暂不计资格。线下或历史付费兑换未自动认定；应先补充明确付费来源的数据模型与审核流程，不拿原总充值字段猜测。

## 有效请求与周期核对

用量成功插入时计入持久日桶：有实际费用、token（含缓存/图像 token）或图像次数等有量记录可计；全零失败占位不计。用户/request_id 去重，日志删除不抹掉资格。活动关闭且用户没有对应未结束周期时不写活动计数。

超过 35 天且无开放周期引用的日期固化后，分批清理去重键；日快照保留，旧请求重放不重新计数。维护每分钟处理最多 100 个周期，按最近检查时间轮转，独立短事务清理最多 5000 个去重键。

闭合日期没有签到可确定中断并释放预算，次日可重开。全部日期达标则到期后幂等结算。受限/软删用户挂起为 `blocked_user`，恢复后再结算，不静默取消承诺。

**当前系统没有跨实例的用量写入完成水位。** 请求不足的闭合周期显示 `pending_usage` 并保留预留，迟到记录达标后继续发奖。管理员在奖励流水页可重核，或在确认请求确实不足、尚未形成奖励权益后带原因取消；取消留审计且不能撤销已达标/已发奖金。请求数不足不会被任意超时自动认定失败。这是保守处理方案，未来如加入完整写入水位，可自动结束真正未达标的周期。

## 接口

| 接口 | 行为 |
|---|---|
| `GET /api/v1/checkin/status` | 业务日、资格、余额、预算状态、奖励与加成、连续周期 |
| `POST /api/v1/checkin/claim` | 空对象/空请求；服务端判定，重复返回原结果 |
| `GET /api/v1/checkin/history` | 自己的奖励记录，cursor/limit |
| `GET /api/v1/checkin/cycle` | 自己的周期，自动结算 |
| `GET/PUT /api/v1/admin/settings/checkin` | 最新规则；写入使用 `{expected_version,config}` 乐观版本 |
| `GET /api/v1/admin/checkin/rewards` | user_id/cursor/limit/date_from/date_to/reward_type 筛选 |
| `GET /api/v1/admin/checkin/budgets` | date_from/date_to/limit；查看原承诺日支出、预留和余量 |
| `GET /api/v1/admin/checkin/cycles` | 用户与游标过滤的周期核对列表 |
| `POST /api/v1/admin/checkin/settlements/:id/resolve` | `{action:"retry"或"cancel",reason}`；原因 5–500 字 |

沿用原成功/错误响应和用户/管理员鉴权、用户面限流、审计与合规守卫。配置冲突与非法结算状态返回可识别错误码，不允许浏览器指定中奖金额。
